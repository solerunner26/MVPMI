Community Contact Directory — build spec
Bilingual (English / ગુજરાતી) Android app for a small community: members submit their details once, an admin approves, approved members get a read-only A–Z directory with call and WhatsApp. This document pairs with the clickable prototype.
← Open the prototype
1 · Platform
Native Android, Kotlin. minSdk 21 (Android 5.0) / targetSdk 36 — this covers every phone still in real use in a small town. Use Views + Material Components (M3 theme) rather than Compose if you must go below API 21; Compose is fine at minSdk 21 and is the recommendation.
Single-module app. Local store: Room (SQLite) for the on-device directory cache; server: Firebase Firestore + Firebase Auth (admin only), or any small REST + Postgres host if you prefer to avoid Google services. Directory reads work offline from Room; writes queue until network returns.
No login for normal members — device identity is the member's phone number, verified once by SMS OTP so nobody can enroll on someone else's behalf. Admin has username + password.
Layout scales by window size class (compact / medium / expanded) so the same screens work on a 5" phone, a 7" tablet and a landscape phone. Text sizes are in sp; the app also honours the OS font-size setting on top of the in-app large-font switch.
2 · Data model
member id uuid pk name text required name_gu text optional (Gujarati spelling) phone text required, unique, E.164 (+91XXXXXXXXXX) village text required tehsil text required district text required status enum pending | approved | removed created_at timestamp approved_at timestamp null until approved approved_by text admin username enrollment_request (module 1 — one open request per phone) id, member_payload (the five fields), phone, created_at, state: open | approved | rejected | withdrawn update_request (module 2e) id, member_id, changed_fields (json: field -> new value), created_at, state: open | authorized | rejected delete_request (module 2f) id, member_id, reason, created_at, state: open | approved | declined archive (admin-only store, module 1c) id, snapshot (json of the submitted fields), source_phone, reason: withdrawn | rejected | removed_on_request | deleted_by_admin, archived_at -- never joined into any member-facing query admin username, password_hash (bcrypt/argon2), phone, password_changed_at, failed_attempts, locked_until
Server rules: a member document is readable only when the requesting phone belongs to an approved member. archive and all *_request collections are admin-read-only. Nothing in the app can write status = approved — only the admin endpoint can.
3 · Rules that decide what a user sees
1
No request, no member record → Entry form (module 1, state A).
2
Open request, not approved → Pending screen (state B) on every launch. Directory is unreachable — not just hidden; the query returns nothing server-side. Only Edit and Withdraw are available.
3
Edit + re-send → old enrollment_request is set to withdrawn, archived, and a fresh open request replaces it in the admin queue. Never two open requests for one phone.
4
Withdraw → request leaves the queue and the payload is copied to archive. The user's device returns to the empty form.
5
Approved → Directory is the launch screen from then on. Read-only: the only writes a member can make are an update request and a delete request, both of which land in the admin queue and change nothing until authorized.
4 · Screen inventory
Module 1 — Entry form; Pending screen; Edit request (same form, replace-on-send).
Module 2 — Directory (sticky search, flat A–Z with letter headers, per-card Call + WhatsApp); My Profile (own card, update request, removal link, large-font switch); Edit my details.
Module 3 — Admin login (show/hide password, strength meter, forgot/reset by OTP, 5-attempt lockout, 90-day change reminder); Reset password; Dashboard with six tabs: New Requests, Update Requests (old vs new side by side), Delete Requests, Members (admin edit/delete directly), Archive, Backup/Restore.
Floating language and theme buttons sit on every screen except the admin login and reset screens.

7 · Backup / restore
Export writes one file through the Storage Access Framework (ACTION_CREATE_DOCUMENT) so it works without storage permissions on every version: community-directory-backup-YYYYMMDD.json (members + all request queues + archive) and a flat community-directory.csv of approved members for printing. Restore uses ACTION_OPEN_DOCUMENT, validates the schema version, shows a diff count, then replaces the local database inside one transaction. Add a weekly automatic export to the admin's Drive folder — a small-town admin will not remember to press the button.
8 · v2 additions (in the current prototype)
· Gujarati is the primary language everywhere, English as the small second line. The floating toggle only swaps which one is large.
· Two numbers per member — phone (personal, required) and phone2 with a label2 of work/other. Each number gets its own call + WhatsApp buttons.
· Validation — every field required; phone must be 10 digits starting 6–9; second number must differ from the first. Digits-only input filtering, live 0/10 counter.
· Village / tehsil spell-check — a dictionary of community villages (Gujarati + Latin) with a normalised Levenshtein match ≤0.42 suggests the correct spelling and auto-fills tehsil + district on tap. Ship the dictionary as app data the admin can extend.
· Directory is village-first — the community is fixed at 7 villages in Mahuva tehsil, Bhavnagar district, so tehsil and district are constants (seed them as app config the admin can extend, not free text). The directory opens on a 7-tile village grid, each tile carrying the sun mark and its live member count; tapping one drills into that village, and an All Members button shows the whole list. Tiles are drag-reorderable and the order is persisted per device. Lists sort alphabetically by Gujarati name; search still activates at 3 characters, spans every village, and flags a single exact hit.
· Live text-size slider (85–165%) on My Profile scales every size and touch target through one root multiplier; store it in preferences and apply on launch.
· Hidden admin door — 5 taps on the app logo → 4-digit access code keypad (prototype code 2468) → admin login. Wrong code or failed login writes a security_alert row (device, OS, the device holder's number when known) and pushes a notification to the admin; the app returns to normal with no hint that an admin area exists. Add exponential back-off after 3 wrong codes.
· Admin dashboard is a tile grid, not a tab strip — all seven areas visible in one glance with live counts, one tap in, back out. New area: Security alerts, with a Block-device action.
· Exports — print-ready A4 PDF contact book (WebView/print framework on Android, or a server-rendered PDF), Excel .xls, full JSON backup, and a share-sheet hand-off so any of them can go straight to a WhatsApp group.
9 · Open questions for you
· One admin or several (a co-admin who can approve but not delete)?
· Should the directory be printable / exportable by ordinary members, or admin only?
· Do you want SMS OTP verification of the phone number at enrollment (recommended, costs a little per message)?
· Hosting: Firebase free tier is enough for a few hundred members — confirm that Google services are acceptable on your users' phones.
